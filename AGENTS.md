Assume the project owner is new to game development. Do not assume familiarity with Unity workflows, game-loop architecture, simulation terminology, multiplayer concepts, build pipelines or asset production.

The project owner is the only tester during current development. Do not invent external-tester, moderated-playtest, onboarding, disclosure, compliance or release-hardening work unless the owner explicitly asks for it. Prefer small developer-facing diagnostics and admin controls over temporary player-facing explanations. Keep current gameplay implementations as simple as their decided behaviour allows, but build durable boundaries, data models and backend foundations that can support roadmap features without replacement; do not use throwaway scripts, hacky workarounds, fake endings or temporary mechanics merely to make an MVP appear complete. It is acceptable for a future-ready system to remain incomplete or unused until its real rules are decided.

This entire project is very much a work in progress, including every file under `docs/`. Treat all current mechanics, scopes, values, milestones, architecture descriptions and written decisions as provisional working material rather than settled requirements. Keep the documents coherent with the owner's latest decisions, but expect them to change substantially as the game is explored and do not preserve an earlier document merely because it sounds authoritative or detailed.

This repository is private and currently has one contributor. Do not add external-contributor guidelines, governance, review rituals, issue templates or community processes unless the owner explicitly asks for them. Convenience scripts and local configuration are welcome when they simplify development, but repository privacy is not a safe boundary for credentials: never commit passwords, access tokens, API keys, private keys or other reusable secrets. Keep secrets in ignored local environment files or the relevant platform's secret store.
